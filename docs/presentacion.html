03 • Base de Datos e Integridad

PostgreSQL: Prevención de Solapamiento Concurrente

El Problema de la Condición de Carrera (Race Condition)

En ventanillas de centros de salud periurbanos, si dos recepcionistas o pacientes intentan reservar exactamente la misma hora (ej. Dr. Rojas a las 09:00) en el mismo milisegundo, una verificación de software ordinaria (SELECT y luego INSERT) falla y provoca dobles citas.

Nuestra Solución a Nivel de Kernel

Implementamos un Índice Único Parcial en PostgreSQL que delega la atomicidad directamente en el motor de base de datos:

-- 01_schema.sql (Supabase)
CREATE UNIQUE INDEX uq_turno_activo
ON public.turnos (id_profesional, fecha, hora)
WHERE estado = 'reservado';

-- Índices B-tree en Claves Foráneas:
CREATE INDEX idx_turnos_paciente 
ON public.turnos(id_paciente);

CREATE INDEX idx_turnos_fecha_hora 
ON public.turnos(fecha, hora);

⚡ Resultado: PostgreSQL rechaza atómicamente la colisión con HTTP 409 Conflict.

04 • Seguridad a Nivel de Base de Datos

Row Level Security (RLS) en Supabase: Anti-BOLA

❌ Lo que la IA sugirió inicialmente (Naive)
CREATE POLICY "permisiva" ON turnos
FOR SELECT TO authenticated
USING (true); -- ⚠️ VULNERABLE A BOLA

Cualquier usuario logueado podía leer o modificar el expediente y turnos médicos de cualquier otro paciente de la comunidad.

✅ Lo implementado humanamente en Supabase
CREATE POLICY "control_estricto_turnos" ON turnos
FOR SELECT TO authenticated
USING (
  id_paciente IN (
    SELECT p.id FROM pacientes p 
    WHERE p.id_usuario = auth.uid()
  ) OR is_admin_or_staff()
);

Vinculación criptográfica obligatoria entre auth.uid() y la fila. Incluye WITH CHECK para updates.

✓ 5 Tablas con RLS Activo ✓ Funciones SECURITY DEFINER Seguras ✓ Doble Barrera (Controlador + Motor BD)
05 • Identidad y Control de Acceso

Autenticación JWT Robusta y Control RBAC

⏱️

Access Token Corto

Vigencia estricta de 15 minutos firmado con HMAC-SHA256. Minimiza drásticamente la ventana de ataque ante eventual secuestro de credenciales.

🔄

Refresh Token (7 días)

Permite rotación segura en /api/v1/auth/refresh. Solo se intercambia para generar nuevos tokens de acceso sin exponer la contraseña nuevamente.

🛡️

Decorador RBAC

@roles_required('admin', 'recepcionista') impide que un paciente acceda a funciones administrativas (Defensa contra BFLA - OWASP API5).

Hashes de Contraseña: PBKDF2 / Bcrypt con factor de coste y salt dinámico criptográfico por usuario.
NIST SP 800-63B
06 • Seguridad Aplicada

Auditoría OWASP API Security Top 10 (2023)

API1:2023 BOLA / IDOR 100% Mitigado

Validación de titularidad en endpoint + RLS en base de datos. Ningún paciente puede ver ni cancelar turnos ajenos.

API2:2023 Broken Authentication 100% Mitigado

Tokens firmados criptográficamente, rechazo de manipulaciones alg: none y rate limit en login.

API3:2023 Mass Assignment 100% Mitigado

Esquemas Marshmallow estrictos con validación regex boliviana (CI, celulares 6/7) rechazando campos no autorizados.

API4 & API8: DoS y Misconfiguration 100% Mitigado

Flask-Limiter (HTTP 429), cabeceras HSTS/CSP/nosniff y manejador centralizado de errores que nunca filtra trazas SQL.
